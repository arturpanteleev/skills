# Аудит: девять измерений

Для каждого измерения указано, **что собрать** (свидетельства) и **критерий уровня**.
Всё, что здесь найдено, идёт в бэклог через `backlog-schema.md`: уровень ниже целевого —
это задача, а не абстрактная оценка.
Ставь уровень по самой высокой строке, для которой есть свидетельство. Сомневаешься между
двумя — бери нижний и объясни, чего не хватило до верхнего: это и есть готовый next step.

Шкала общая: 0 нет · 1 ad-hoc · 2 повторяемо · 3 управляемо (гейт) · 4 самокорректируется (гейт + тренд).

---

## 1. Архитектура и эволюционируемость

**Что собрать**
- Топ-20 файлов по числу строк; есть ли файлы-монстры (> 800 строк — сигнал, > 2000 — почти всегда проблема).
- Слои/модули: совпадает ли структура папок с заявленной в документации.
- Циклические зависимости — инструментом, если он есть в проекте, иначе выборочно по импортам hotspot-файлов.
- Git-hotspots и change coupling (`probes.md`): файлы, которые всегда меняются вместе, — скрытая связность, которой нет в графе импортов.
- Extensibility drill (`probes.md`): сколько мест надо тронуть, чтобы добавить типовую новую сущность домена.
- Есть ли тест/линтер, запрещающий импорт через внутренности чужого модуля.

**Уровни**

| | Критерий |
|---|---|
| 0 | Слоёв нет, логика и ввод-вывод перемешаны, есть god-файлы, дубли бизнес-правил в нескольких местах |
| 1 | Слои угадываются по названиям папок, соблюдаются по традиции; нарушения встречаются и никого не останавливают |
| 2 | Границы и публичные точки входа описаны в документации; нарушений мало, но ловятся только на ревью |
| 3 | Граница исполняема: линтер или архитектурный тест блокирует запрещённый импорт и цикл |
| 4 | Плюс числовой тренд (связность, fan-out, touch-count расширения) с ratchet — ухудшение не проходит молча |

**Частые findings**: god-файл в топе hotspot'ов (меняется часто И огромный — чинить первым);
добавление одной сущности требует правки в N > 3 файлах; пара файлов с change coupling > 70%;
«слой» существует только в документации.

## 2. Качество кода

**Что собрать**
- Есть ли линтер и форматтер, их строгость (strict-режим типов, включён ли type-aware линт).
- Прогон линтера/типов начисто: сколько ошибок и предупреждений.
- **Число подавлений**: `eslint-disable`, `@ts-ignore`/`@ts-expect-error`, `# type: ignore`, `//nolint`, `# noqa`, `#pragma warning disable`. Растущее число подавлений — самый честный универсальный индикатор гниения.
- `TODO`/`FIXME`/`HACK`/`XXX` с датами: сколько и насколько старые.
- Мёртвый код и неиспользуемые зависимости (для JS/TS — `knip`, если можно запустить без установки в проект; иначе выборочно).
- Версия языка/рантайма относительно актуальной; используются ли современные конструкции или наследие.
- Копипаста: сравни 2–3 подозрительных пары файлов из change coupling.

**Уровни**

| | Критерий |
|---|---|
| 0 | Линтера нет или он не проходит; стиль у каждого файла свой |
| 1 | Линтер есть, но с послаблениями и локальными подавлениями «чтобы прошло» |
| 2 | Линтер и форматтер проходят начисто локально, конфиг осмысленный, но в CI не обязательны |
| 3 | Линт и типы — блокирующий гейт в CI; подавления требуют комментария-обоснования |
| 4 | Плюс ratchet на сложность/дубли/подавления: новый код не может быть хуже текущего уровня |

**Частые findings**: подавлений больше, чем осмысленных правил; `TODO` старше года;
дублирующаяся бизнес-логика в двух слоях; устаревшая версия рантайма без EOL-плана.

## 3. Тесты и верификация

**Что собрать**
- Есть ли тесты, сколько, отношение строк тестов к строкам продуктового кода.
- Прогон: проходят ли, сколько времени, есть ли пропущенные/skip.
- Покрытие — только из вывода инструмента; отдельно посмотри покрытие **критических** путей (деньги, доступ, внешние ответы, миграции), а не среднее по больнице.
- **Качество, а не количество**: открой 3 случайных теста. Есть ли настоящие ассерты? Тест, который вызывает функцию и проверяет, что не упало, покрытие даёт, а регрессию не ловит.
- Что заявлено непокрытым в документации проекта — и правда ли это весь список.
- Фикстуры внешних API: повторяют реальный контракт или выглядят правдоподобно.

**Уровни**

| | Критерий |
|---|---|
| 0 | Тестов нет или они не запускаются |
| 1 | Тесты есть на отдельные куски, запускаются вручную, часть постоянно падает или отключена |
| 2 | Набор стабильный и воспроизводимый одной командой; критические пути покрыты неравномерно |
| 3 | Тесты обязательны в CI, есть порог покрытия, критические пути покрыты осознанно |
| 4 | Плюс защита от иллюзии покрытия: ratchet на покрытие, mutation-тесты или property-based на ключевых функциях; явный документированный список того, что НЕ покрыто |

**Частые findings**: покрытие 80%, но ассертов нет; критический модуль покрыт хуже среднего;
фикстура не совпадает с реальным ответом API; skip-тесты, которые никто не заметил.

## 4. Безопасность и контроль данных

**Что собрать** — по [OWASP Top 10:2025](https://owasp.org/Top10/2025/):

| Категория | Что проверить в этом репозитории |
|---|---|
| A01 Broken Access Control | У каждого эндпоинта/команды есть проверка прав? Проверка на сервере, а не в UI? IDOR: объект берётся по id из запроса без проверки владельца? SSRF: пользовательский URL уходит в запрос? |
| A02 Security Misconfiguration | CORS `*` на аутентифицированных ручках, debug в проде, дефолтные пароли, открытые порты, стектрейсы наружу, права токенов CI |
| A03 Supply Chain Failures | см. измерение 5 — но уязвимость high/critical считается и здесь |
| A04 Cryptographic Failures | Пароли и токены: хеширование, а не шифрование; TLS; секреты в логах; слабые алгоритмы |
| A05 Injection | SQL/NoSQL/shell/шаблоны: параметризованы ли запросы; конкатенация строк в запрос; prompt injection, если есть LLM |
| A06 Insecure Design | Есть ли rate limit, лимиты размеров, идемпотентность там, где повтор опасен |
| A07 Authentication Failures | Сессии, срок жизни токенов, ротация, брутфорс-защита, восстановление пароля |
| A08 Data Integrity Failures | Верификация подписей вебхуков, непиннованные зависимости и CI-actions, десериализация недоверенных данных |
| A09 Logging & Alerting Failures | Логируются ли события безопасности; не логируются ли секреты и PII; есть ли кому среагировать |
| A10 Mishandling of Exceptional Conditions | **Схлопываются ли разные состояния ошибок в одно.** «Источник недоступен», «источник вернул пусто» и «проверка неприменима» — разные вещи; если код или отчёт превращает их в один `null`, это баг класса A10. Сюда же: проглоченные исключения, `catch {}`, fail-open вместо fail-closed |

**Контроль данных** (отдельно от OWASP, но в этом же измерении)
- Инвентарь: какие персональные/чувствительные данные проект трогает и где они оседают.
- Что уходит во внешние сервисы (включая LLM-провайдеров и телеметрию) — и не уезжают ли туда секреты или полные дампы.
- Ретеншн и удаление; доступ к бэкапам.
- Read-only границы: где заявлено «только чтение» — действительно ли нет write-пути.

**Секреты**
- Секрет-скан истории коммитов, а не только рабочего дерева.
- `.env` в гите; ключи в примерах конфигов; токены в тестовых фикстурах; секреты в CI-логах.

**Уровни**

| | Критерий |
|---|---|
| 0 | Найден живой секрет, или отсутствует авторизация там, где она нужна |
| 1 | Базовая аутентификация есть, остальное не рассматривалось; секрет-скана нет |
| 2 | Практики описаны и в целом соблюдаются, проверяются глазами на ревью |
| 3 | Секрет-скан и аудит зависимостей — блокирующие; авторизация проверяется тестами; границы данных описаны и исполняемы |
| 4 | Плюс регулярная переоценка модели угроз, логирование событий безопасности с алертами, отработанный отзыв доступа |

**Частые findings**: `catch {}` вокруг вызова, от которого зависит решение; CORS `*` рядом с
куками; секрет в истории коммитов (ротация обязательна, удаления из истории мало);
проверка прав в одном транспорте и её отсутствие в другом.

## 5. Цепочка поставок

**Что собрать**
- Аудит уязвимостей штатным инструментом экосистемы; отдельно — high/critical.
- Устаревание: сколько прямых зависимостей отстаёт на мажор и насколько давно.
- Lockfile: есть, закоммичен, соответствует манифесту.
- Заброшенные пакеты: последняя публикация больше 2 лет назад при живой альтернативе.
- Автообновления: Dependabot/Renovate — настроены и **не накопили ли открытых PR**.
- CI: внешние actions/образы пиннованы на SHA или на подвижный тег.
- Число прямых зависимостей: каждая — это доверие чужому мейнтейнеру.

**Уровни**

| | Критерий |
|---|---|
| 0 | Lockfile отсутствует либо есть незакрытые critical-уязвимости |
| 1 | Обновляются по случаю, когда что-то сломалось |
| 2 | Есть регулярная ручная практика обновления, lockfile под контролем |
| 3 | Аудит блокирует сборку на high/critical; автообновления включены; CI-зависимости пиннованы |
| 4 | Плюс обновления реально доезжают (очередь автоPR не копится), есть политика по мажорам и SBOM/провенанс |

## 6. Производительность и стоимость

**Что собрать**
- **N+1**: запрос к БД или сетевой вызов внутри цикла — ищи `for`/`while`/`map` с `await`/query внутри.
- Индексы: колонки в `WHERE`/`JOIN`/внешние ключи без индекса; `SELECT *` на широких таблицах.
- Пагинация: выгребается ли неограниченный список.
- Внешние вызовы: таймаут, ретрай с backoff, circuit breaker, бюджет на запрос. Отсутствие таймаута — почти всегда finding.
- Блокирующие операции в горячем пути; синхронный I/O в однопоточном рантайме.
- Кэширование там, где данные меняются редко.
- Для фронтенда: размер бандла, лишние зависимости, отсутствие code splitting.
- Стоимость: если есть платные вызовы (LLM, внешние API) — считается ли цена запроса, есть ли лимит.
- Есть ли хоть какие-то замеры. **Отсутствие измерений — это уровень, а не «наверное, нормально».**

**Уровни**

| | Критерий |
|---|---|
| 0 | Есть очевидные N+1 или неограниченные выборки в горячем пути; измерений нет |
| 1 | Проблемы находят по жалобам пользователей |
| 2 | Известные узкие места задокументированы, есть ручные замеры |
| 3 | Таймауты, лимиты и бюджеты заданы в коде; критичные пути замерены; есть метрики в рантайме |
| 4 | Плюс бюджеты производительности проверяются автоматически и регресс блокируется |

## 7. Документация как спецификация

Ключевой критерий пользователя: **если код исчезнет, можно ли по документации восстановить
сервис?** Проверяется не объёмом текста, а reconstruction-пробой (`probes.md`).

**Что собрать**
- Есть ли точка входа и не противоречат ли друг другу разные документы.
- Свежесть: дата последнего изменения `docs/` против `src/`; упоминания файлов, команд, флагов и эндпоинтов, которых больше нет.
- Соответствие: возьми 3 утверждения из документации и проверь их по коду. Возьми 3 недавние фичи из git-истории и проверь, отражены ли они в документации.
- **Reconstruction-проба** по одному модулю: по документации выпиши назначение, вход/выход, инварианты, ошибки и зависимости; сверь с кодом; посчитай, какая доля контракта восстановима.
- Описаны ли решения и их причины (ADR или эквивалент) — или только «что», без «почему».
- Для внешнего API: есть ли машиночитаемая спецификация и генерится ли она из кода.

**Уровни**

| | Критерий |
|---|---|
| 0 | Документации нет либо она заведомо неверна |
| 1 | README с инструкцией запуска; остальное — в головах |
| 2 | Структурированная документация, актуальная на глаз; расхождения находятся при чтении |
| 3 | Документация проверяется автоматикой (сборка, ссылки, drift-тесты), у каждого раздела есть владеющий код |
| 4 | Документация первична: контракт описан до реализации, генерация/проверка двусторонняя, reconstruction-проба проходит |

**Частые findings**: фича есть в коде, но её нет в документации (документация всегда отстаёт
по фичам, добавленным «быстро»); команда из README не существует; описано «что», не описано
«почему» — и решение уже нарушено дважды.

## 8. Деплоируемость и эксплуатация

**Критерий: девопс, впервые видящий репозиторий, может выкатить и откатить его, ни о чём не спрашивая.**

**Что собрать**
- Сборка и артефакт: воспроизводимая сборка, образ/пакет, зафиксированные версии базового образа.
- **Инвентарь переменных окружения** (`probes.md`): все читаемые из кода переменные против описанных. Расхождение в любую сторону — finding. Отдельно: что обязательно, что имеет дефолт, что является секретом, падает ли сервис на старте при отсутствии обязательной.
- Миграции состояния: есть ли механизм, применяются ли автоматически, обратимы ли, что будет при откате кода вперёд-назад.
- Масштабирование: stateless ли процесс, что будет при двух репликах (локальное состояние, планировщики, кеши в памяти, гонки за задачи).
- Готовность: health/readiness-проба, graceful shutdown, поведение при недоступной зависимости на старте.
- Наблюдаемость: структурные логи, метрики, трассировка, алерты — и есть ли кому на них реагировать.
- Откат: как вернуться на прошлую версию; что при этом произойдёт с данными.
- Runbook: что делать при типовом сбое; кто владелец.

**Уровни**

| | Критерий |
|---|---|
| 0 | Как это разворачивается — знает только автор; переменные окружения нигде не перечислены |
| 1 | Есть инструкция запуска на машине разработчика, прод — вручную |
| 2 | Есть воспроизводимая сборка и полный список переменных; деплой описан, но выполняется руками |
| 3 | Деплой автоматизирован, миграции и откат описаны и проверены, есть health-проба и структурные логи |
| 4 | Плюс отрепетированный откат, алерты с владельцем, SLO и runbook на типовые сбои |

**Частые findings**: переменная читается в коде, но её нет в примере конфига (сервис
молча работает на дефолте в проде); миграций нет вовсе — схема «появляется сама»;
состояние в памяти процесса ломает вторую реплику; нет graceful shutdown — запросы рвутся на деплое.

## 9. Конфигурируемость и продуктовая связность

**Что собрать**
- Хардкод: URL и хосты, пути, лимиты и таймауты числами в коде, идентификаторы окружений, бизнес-пороги, magic numbers. Отдельно ищи `localhost`, IP-адреса, внутренние домены, имена людей и каналов.
- Разделение конфигурации и кода: можно ли поднять второй экземпляр в другом окружении, не трогая исходники.
- Feature flags: есть ли способ выключить фичу без релиза; мёртвые флаги, которые давно включены.
- Заявленное против реализованного: возьми обещания README и проверь по коду. Честны ли статусы зрелости («прототип», «в разработке», «работает»).
- Границы продукта: понятно ли из репозитория, что проект делает и чего он осознанно не делает.
- Дрейф назначения: проект, начинавшийся как X, а ставший Y, обычно накапливает имена, документацию и модули от X — перечисли такие места.

**Уровни**

| | Критерий |
|---|---|
| 0 | Окружение зашито в код; чтобы развернуть иначе, нужно править исходники |
| 1 | Часть настроек вынесена, часть захардкожена; дефолты подходят только одной машине |
| 2 | Вся конфигурация снаружи и документирована; бизнес-пороги в конфиге, а не в коде |
| 3 | Конфигурация валидируется на старте, есть флаги для рискованных фич, README соответствует коду |
| 4 | Плюс автоматическая проверка соответствия конфигурации, документации и кода; мёртвые флаги удаляются по процессу |

**Частые findings**: `localhost` в коде, который доедет до прода; порог бизнес-правила
числом внутри функции; README описывает продукт, которым проект был полгода назад.
