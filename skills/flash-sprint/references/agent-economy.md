# Экономия лимита при параллельном исполнении

Цель — меньше квоты на принятую задачу, а не меньше токенов на шаг. Считай задачу вместе
с кругами ревью, починкой CI и прод-проверкой. Правила ниже выведены из спринта, где лимит
кончался раньше работы: основную цену дали не постановки, а ожидание внутри модели,
повторные слияния, полные круги ревью и раздутый контекст оркестратора.

## Модель ожидает только тогда, когда есть что решать

- Исполнитель после пуша не держит мониторы, таймеры и циклы `gh pr checks`. Он пишет
  записку передачи (ниже) и завершается.
- Состояние PR отслеживает один скрипт у оркестратора: `scripts/pr-watch.sh` печатает только
  переходы (`CLEAN`, `BEHIND`, `DIRTY`, `fail=N`, `MERGED`). Пустые «ещё идёт» в модель не
  попадают.
- На упавший CI будится исполнитель с узким брифом: какая проверка, ссылка на лог, SHA.
  Флейк (известный таймаут, установка зависимостей, дрейф снимков) оркестратор перезапускает
  сам, без агента.
- Не держи кэш «тёплым» пустыми сообщениями и не отвечай на уведомления без действия.

## Жизненный цикл агента

- Исполнитель живёт до мержа своего PR, затем его останавливают. Ревьюер всегда одноразовый.
- Возобновлять старого агента — когда пауза короткая и нужен его контекст. После долгого
  ожидания дешевле новый агент с запиской передачи и конкретной ошибкой.
- После сброса лимита возобновляй только тех, у кого есть незавершённое действие.

## Записка передачи

```text
Задача: ID, ожидаемое поведение. Ветка, worktree, PR, head SHA.
Изменены: файлы. Проверки: команда → результат, ссылка на лог.
Отвергнутые гипотезы и почему. Решения владельца.
Ждём: что именно (CI run, ревью, человек). Следующий шаг и критерий готовности.
```

## Роли и модели

Модель выбирается по цене законченной задачи, не по престижу роли. Если роль в проекте
задана явно — используй её; иначе по умолчанию:

| Работа | Модель | Effort |
|---|---|---|
| Поиск по коду, сбор статусов, Jira/HTML-механика | самая дешёвая или скрипт | — |
| Обычная реализация пакета | средняя (Sonnet) | high |
| Безопасность, контракты, сложная диагностика | старшая (Opus) | high |
| Первый круг ревью | старшая | high; xhigh только для промптов, секретов, внешнего ответа |
| Повторные круги ревью | средняя | high, дельта-ревью |

Эскалация на старшую модель — при отсутствии прогресса после двух попыток, а не заранее.

## Размер пакета и параллельность

- Пакет — не больше 3–4 задач или ~800 строк дифа. Больше — два PR. Большой PR дороже
  каждым кругом ревью и каждым слиянием master.
- Активно 4–6 исполнителей; остальные задачи ждут в очереди без агента. Больше активных
  агентов быстрее съедают пятичасовое окно и перегружают раннеры CI — ожидание растёт.

## Слияния и сгенерированные файлы

- Мержи по одному, но планируй порядок заранее: PR с общими файлами и номерами миграций —
  подряд, с явно названным владельцем стыка.
- Конфликты в сгенерированных файлах (собранная документация, реестры, счётчики, номера
  миграций) разрешай перегенерацией, а не правкой руками и не агентом старшей модели.
- Если проект требует свежую ветку перед мержем, а очередь длинная — предложи владельцу merge
  queue. Само изменение настроек репозитория — его решение.

## Контекст оркестратора

- Внешнюю механику (переходы Jira, комментарии, `gh`, сборку HTML) делай скриптом или
  дешёвым агентом с однострочным итогом. Полные ответы API в контекст оркестратора не тащи.
- На границах фаз («все PR открыты», «ревью закончено», «всё смержено», «выкачено») сохрани
  состояние в файл и сделай `/compact` с явным списком: что сохранить, что выбросить.
- Перед очисткой контекста запиши, какие агенты и фоновые задачи ещё живы.

## Брифы

- Общий бриф исполнителя и ревьюера — отдельным файлом в scratchpad, в промпте только
  пакет и ссылка. Указывай проверенные пути к модулям и командам, чтобы агент не изучал
  проект заново.
- Пути для временных файлов — уникальные в worktree агента. Общий временный файл между
  параллельными агентами перепутывает результаты.
- Обязательное чтение правил проекта соблюдай как есть; сокращать его — решение владельца.

## Замер

Перед спринтом и на границах фаз снимай `/usage`. В отчёте спринта: число агентов и кругов
ревью, повторные CI, платные прогоны, использованная квота на принятую задачу. Сравнивай
волны сопоставимых задач, а не одиночные случаи.
