# HTML спринта и долговременное состояние

## Шаблон по умолчанию

Новый спринт собирается шаблоном из `template/` (правила текста, оформление и пример данных — `template/README.md`). Ниже общие требования к состоянию и проверке; описание «таблица по группам» в разделе «Представление» относится к спринтам, где владелец просил именно таблицу. Шаблон использует семь статусов: 0 Не взято, 1 В работе, 2 Ревью, 3 Смержено, 4 На проде, 5 Готово без PR, 6 Нужен человек (файл `sprint_status.json`, версия схемы 1 сохраняется).

## Продолжение существующего артефакта

Найди HTML, генератор, файл состояния и инструкцию сборки. До записи прочитай текущее содержимое и проверь параллельные изменения. Сохрани список ID и текущие статусы для сравнения после сборки. Используй имеющуюся реализацию вместо создания нового приложения.

В последнем варианте FormatsBot артефакты находятся вне основного репозитория в `formats-bot-artifacts/`: `build_sprint.py`, `sprint_status.json`, `formats-bot-sprint.html`. Это пример, а не обязательный путь для других проектов. Не копируй его специфические задачи, группы, даты, аккаунты и URL в другой спринт.

## Представление

- Вводная: цель, выбранный объём, дата проверки, ограничения и первоисточники.
- Таблицы по смысловым группам: ID, задача, статус работы, отдельная колонка Jira со ссылками и датой снимка.
- Подробные карточки с постоянными якорями ID и возвратом к таблице.
- Источники, зависимости, блокеры и приёмка доступны без скрытой функциональности.
- Статус таблицы и карточки согласован. Цвет сопровождается текстом; элементы управления подписаны, работают с клавиатуры; таблицы доступны на узком экране.
- Для автономного файла — экспорт обновлённого HTML со встроенными статусами, печать/PDF без кнопок. Встраивай данные безопасно, экранируя HTML и закрытие script; не добавляй секреты.

Не делай обязательным сайт, сервер, хостинг или внешний сервис: локальный HTML — полноценный результат.

## Состояние

Разделяй описания задач и их состояние. Для нового спринта используй простой файл состояния с версией схемы, ID спринта, обновлением и словарём по ID задач; PR/Jira, дату проверки и блокеры можно хранить рядом. В существующем спринте не меняй схему без необходимости и явной миграции с сохранением значений.

В FormatsBot уже используется `sprint_status.json` с `updatedAt` (Unix milliseconds) и `statuses` (ID → число): 0 — «Не взято», 1 — «В работе», 2 — «На GitHub», 3 — «Смержено». Версия 1 добавляется генератором во встроенное состояние HTML. Сохрани этот контракт при обновлении существующего спринта.

- Генератор загружает сохранённое состояние; новый ID получает начальный статус, старые сохраняются. Не добавляй ключи, не существующие в задачах, молча: отчитайся об осиротевших значениях и выясни, удалена ли задача намеренно.
- `localStorage` — удобный кэш текущего браузера, а не синхронизация с файлом, другим браузером или Logos. Сам HTML не может незаметно переписать соседний JSON.
- Если пользователь менял статусы в браузере, используй его свежий экспорт/явный импорт состояния перед пересборкой. Когда такой экспорт недоступен, обозначь границу видимости; не заявляй сохранность невидимых браузерных правок.
- Сравнивай состояния одного спринта; чужой ID спринта или неизвестную схему не импортируй автоматически. В старой схеме без ID сначала установи принадлежность по артефакту и задачам.
- Более новый timestamp помогает обнаружить расхождение, но сам по себе не доказывает правильность статуса. Конфликтующие изменения по одной задаче сверяй с владельцем/источниками, не затирай весь набор правилом last-write-wins.
- Когда агент обновляет статусы, сначала сохраняет их в файле состояния, затем пересобирает HTML. Когда меняет состав/текст — редактирует источник генерации.
- Обновление HTML не меняет Jira и GitHub. Merged, deployed и accepted — разные факты.

## Проверка

1. Запусти штатный генератор и проверь успешный выход.
2. Сверь уникальность ID, группы, внутренние ссылки, соответствие таблиц карточкам и наличие состояния для каждой задачи.
3. Проверь, что неизменённые задачи сохранили статусы, а новые не перетёрли старые.
4. При новом/изменённом UI открой HTML: обзор, карточка, узкий экран; измени статус, проверь обе подписи, экспортируй и открой экспорт. Свежий экспорт должен сохранить статус без опоры на кэш браузера.
5. Проверь, что повторная сборка из сохранённых источников воспроизводит данные и статусы. Не изменяй исходное состояние ради проверки UI; используй временную копию.

Не перезапускай CI всего продукта из-за изменения текста спринта; проверки продукта нужны при изменении его кода или по обязательным правилам проекта.
