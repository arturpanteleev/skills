# Универсальные зонды

Измерения, которых нет ни в одном линтере и которые работают на любом стеке.
Команды написаны под POSIX-shell и git; расширения файлов подставляй под язык проекта.
Везде исключай служебные каталоги: `node_modules`, `.git`, `dist`, `build`, `vendor`,
`target`, `.venv`, `coverage`.

---

## 1. Hotspots: где на самом деле живёт риск

Файл, который часто меняется **и** большой, — первый кандидат на рефакторинг.
Файл, который большой, но не менялся год, трогать не нужно.

```sh
# Топ изменяемых файлов за год
git log --since="12 months ago" --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -20

# Топ файлов по размеру (подставь расширения проекта)
find . -path ./node_modules -prune -o -name '*.ts' -print \
  | xargs wc -l | sort -rn | head -20
```

Пересечение двух списков и есть список работ по измерению 1. Его и приоритизируй,
а не «все файлы больше 500 строк».

---

## 2. Change coupling: связность, которой нет в импортах

Два файла, которые всегда меняются в одном коммите, связаны — даже если не импортируют
друг друга. Это ловит дублированную логику, «параллельные» слои и забытые обязательства
(поменял хендлер — не забудь схему).

```sh
# Что меняется вместе с конкретным файлом
F=path/to/hotspot
git log --since="12 months ago" --pretty=format:%H -- "$F" \
  | while read c; do git show --pretty=format: --name-only "$c"; done \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -10
```

Читай как долю: если файл менялся 40 раз и в 32 из них менялся и второй — это 80%.
Выше 70% при отсутствии явной связи в коде — finding.

## 3. Инвентарь переменных окружения

Самый частый и самый дешёвый источник инцидентов деплоя.

```sh
# Что код реально читает. Точечная и скобочная формы, четыре экосистемы.
grep -rhoE 'process\.env(\.[A-Za-z0-9_]+|\[["'"'"'][A-Za-z0-9_]+["'"'"']\])|os\.Getenv\(["'"'"'][A-Za-z0-9_]+|os\.environ[.[]get?\(?["'"'"'][A-Za-z0-9_]+|ENV\[["'"'"'][A-Za-z0-9_]+' \
  --include='*.ts' --include='*.tsx' --include='*.js' --include='*.go' --include='*.py' --include='*.rb' \
  --exclude-dir=node_modules . \
  | tr -c 'A-Za-z0-9_\n' '\n' | grep -E '^[A-Z][A-Z0-9_]{2,}$' | sort -u > /tmp/code_env.txt

# Что описано (подставь реальный файл: env.example, .env.sample, compose, values.yaml)
grep -oE '^[A-Z][A-Z0-9_]+=' env.example | tr -d '=' | sort -u > /tmp/doc_env.txt

comm -23 /tmp/code_env.txt /tmp/doc_env.txt   # читается, но НЕ описано
comm -13 /tmp/code_env.txt /tmp/doc_env.txt   # описано, но НЕ читается
```

**Калибровка — обязательна перед тем, как делать вывод.** Сравни размер найденного списка
с размером файла-примера. Если код читает 2 переменные, а в примере их 105 — сломан зонд,
а не проект. Типичные причины: скобочная форма `process.env["NAME"]` вместо точечной
(включается `noPropertyAccessFromIndexSignature`), собственный хелпер `env("NAME")`,
чтение через библиотеку конфигурации, иные расширения файлов.

Тогда найди центральный конфиг-модуль и читай список оттуда:
```sh
grep -rc 'process\.env\|os\.Getenv\|os\.environ' --include='*.ts' --include='*.go' --include='*.py' \
  --exclude-dir=node_modules . | grep -v ':0$' | sort -t: -k2 -rn | head -5
```
Файл с наибольшим числом вхождений почти всегда и есть конфигурационный слой.

**Динамический доступ** (`process.env[name]`, чтение по списку ключей) статическим поиском
не ловится в принципе. Увидел такую строку — пометь инвентарь как неполный и скажи это
в отчёте вместо того, чтобы выдавать неполный список за полный.

Три класса findings:
- **читается, но нигде не описана** — деплой молча уедет на дефолте;
- **описана, но не читается** — мусор, вводящий в заблуждение, либо мёртвая фича;
- **описана, но не помечена как секрет** — попадёт в лог или в репозиторий.

Отдельно проверь: падает ли процесс на старте, если обязательная переменная не задана.
Тихий дефолт вместо падения — finding.

## 4. Хардкод и секреты

```sh
# Хосты, адреса и порты в коде
grep -rnE 'https?://(localhost|127\.0\.0\.1|0\.0\.0\.0|([0-9]{1,3}\.){3}[0-9]{1,3})' \
  --exclude-dir=node_modules --exclude-dir=.git --exclude-dir=dist . | head -40

# Паттерны секретов в рабочем дереве
grep -rnE '(api[_-]?key|secret|passwd|password|token|private[_-]?key)["'"'"']?\s*[:=]\s*["'"'"'][^"'"'"']{12,}' \
  --exclude-dir=node_modules --exclude-dir=.git . | head -40

# Секреты в истории — важнее рабочего дерева
git log -p --all -S'BEGIN PRIVATE KEY' --oneline | head
git log --all --name-only --pretty=format: | sort -u | grep -E '^\.env|\.pem$|\.p12$|credentials'
```

Найденный секрет в истории требует **ротации**. Удалить файл из истории недостаточно и
почти всегда уже поздно — считай его скомпрометированным.

## 5. Подавления и долг

Число подавлений линтера — самый честный индикатор гниения на любом языке.

```sh
grep -rnE '@ts-ignore|@ts-expect-error|eslint-disable|# *type: *ignore|# *noqa|//nolint|#pragma warning disable' \
  --exclude-dir=node_modules --exclude-dir=.git . | wc -l

grep -rnE '\b(TODO|FIXME|HACK|XXX)\b' --exclude-dir=node_modules --exclude-dir=.git . | wc -l
```

Для 3 самых подозрительных — узнай возраст: `git log -1 --format='%ad %an' -S'<текст TODO>' -- <файл>`.
`TODO` старше года — это не задача, это принятое решение, которое никто не признал.

## 6. Запросы и вызовы в циклах

```sh
# Если есть ripgrep — многострочный поиск await внутри цикла
rg -U --multiline 'for\s*\([^)]*\)\s*\{[^}]*await' -g '!node_modules' -n | head -20
rg -U --multiline '\.(map|forEach)\([^)]*(async|await)' -g '!node_modules' -n | head -20
```

Без ripgrep — открой top-5 hotspot-файлов, работающих с БД или сетью, и прочитай их циклы
глазами. Дополнительно проверь: у каждого внешнего вызова есть таймаут? есть ли
неограниченная выборка без пагинации? есть ли `SELECT *` на широкой таблице?

## 7. Reconstruction-проба: документация как ТЗ

Отвечает на вопрос «если код исчезнет, восстановит ли его другой исполнитель по документации».

1. Выбери **один** модуль из hotspot-списка — не точку входа, а содержательный кусок домена.
2. **Не открывая код**, по одной только документации выпиши его контракт:
   назначение · публичный интерфейс с сигнатурами · инварианты и предусловия ·
   обрабатываемые ошибки и что происходит при каждой · зависимости · побочные эффекты.
3. Теперь открой код и сверь по пунктам.
4. Посчитай: восстановимо полностью / восстановимо частично / отсутствует / **описано неверно**.

Неверное описание хуже отсутствующего: по нему исполнитель уверенно сделает не то.
Такие пункты всегда идут в findings как major, даже если документации в целом много.

Каждый прогон бери новый модуль — за несколько прогонов обойдутся все.

## 8. Extensibility drill: измеряем open-closed

1. Найди типовую расширяемую сущность проекта: плагин, хендлер, роут, команда, стратегия,
   сценарий, адаптер источника.
2. Возьми один существующий экземпляр и его идентификатор:
   ```sh
   grep -rn 'существующий_идентификатор' --exclude-dir=node_modules --exclude-dir=.git . | cut -d: -f1 | sort | uniq -c | sort -rn
   ```
3. Посчитай, сколько файлов пришлось бы тронуть, чтобы добавить рядом новый, и раздели их:
   - **регистрация** в одном реестре — норма;
   - **тесты и документация** — норма;
   - **маппинг в UI / каталоге / переводах** — терпимо, но лучше выводить из реестра;
   - **`switch`/`if` по типу в логике** — нарушение open-closed, каждое такое место это finding.
4. Норма: 1–3 файла плюс тесты и документация. Больше 5 мест с логикой — архитектура закрыта
   для расширения, и каждая новая фича будет дороже предыдущей.

Записывай полученное число в отчёт: между прогонами его рост — самый ранний сигнал
архитектурной деградации, задолго до того, как это заметит линтер.

## 9. Заявленное против реализованного

```sh
# Последние фичи
git log --since="3 months ago" --pretty=format:'%ad %s' --date=short | head -30
# Когда в последний раз трогали документацию против кода
git log -1 --format=%ad -- docs README.md
git log -1 --format=%ad -- src
```

Возьми 3 фичи из истории и проверь, отражены ли они в документации. Возьми 3 утверждения
из README и проверь по коду. Разрыв в датах больше пары месяцев почти всегда означает,
что документация описывает прошлую версию продукта.
