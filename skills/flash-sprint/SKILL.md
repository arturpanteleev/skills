# FlashSprint

Спринт здесь — рабочий набор задач с постоянными ID, понятным результатом и интерактивным HTML, по которому владелец и агент обсуждают работу и обновляют статусы между сессиями. Он может быть продуктовым, техническим, исследовательским или смешанным. Не навязывай Scrum-ритуалы, фиксированную длительность или лимит 15 задач.

## Выбрать режим

- **Собрать:** превратить диктовку, идеи и проблемы в задачи; обсудить дорогие развилки и подготовить HTML.
- **Уточнить:** сверить задачи с источниками, дополнить приёмку, зависимости и вопросы.
- **Продолжить / обновить:** найти существующий артефакт, восстановить состояние, сверить Jira/PR и обновить HTML.
- **Выполнить:** реализовать явно выбранный объём с проверками и ревью.
- **Отчитаться:** показать результат, подтверждения и оставшуюся работу.
- **Аудит:** только когда нужен по запросу или конкретной задаче; глубина — по `references/discovery.md`, `references/probes.md`, `references/audit.md`.

«Поработаем по спринту» само по себе означает работу с планом и артефактом. Учитывай уже выданное разрешение на исполнение; не спрашивай повторно о каждом шаге одобренной работы. Не выводи разрешение на merge, deploy или внешнюю публикацию только из слова «спринт».

## Найти текущий спринт

Прочитай инструкции проекта. Проверь рабочее дерево перед изменениями; сохраняй чужие незавершённые правки. Не требуй чистоты всего дерева для независимого изменения артефакта.

По текущему чату, соседним чатам (если доступно), личным заметкам и артефактам установи:

- какой продукт и репозиторий обсуждаются;
- путь HTML, его генератора и файла состояния;
- выбранный объём, группы, ID, ссылки на Jira/PR и открытые блокеры.

Сначала используй известные пути и целевые поиски. Название папки само по себе не доказывает, что это нужный продукт. Если несколько спринтов подходят одинаково, уточни выбор; не начинай новый вместо существующего.

## Из диктовки в задачи

Сначала сохрани смысл пожелания владельца, затем проверь существенные предположения. Не превращай идею в доказанный дефект. Источники: сообщение владельца, конкретный кейс, код, Jira с комментариями, PR, результаты проверок. Недоступное помечай «не проверено» и объясняй, что именно неизвестно.

Разделяй желаемое поведение, текущее состояние и гипотезу причины. Для проблем данных различай отсутствие источника/адаптера, отказ прав, неверный срез/период, короткую историю, таймаут и неверную интерпретацию. Собственный ответ диагностического бота не доказывает причину.

Дедуплицируй, выделяй независимо принимаемые результаты, отдельно обозначай исследование с решением и владельцем. Технические улучшения не добавляй автоматически в продуктовый спринт. Сохраняй заданные приоритеты и группы; предложения изменить их называй явно. Не обрезай список до произвольного числа.

Формат карточки и ID — [references/backlog-schema.md](references/backlog-schema.md).

## HTML и сохраняемое состояние

Следуй [references/sprint-artifact.md](references/sprint-artifact.md): таблица по группам, подробные карточки, постоянные якоря, статусы, ссылки на источники, экспорт и восстановление состояния.

Если генератор существует, редактируй источник и пересобирай; ручная правка результата пропадёт при следующей сборке. Состояние храни отдельно от описаний. Не сбрасывай его при добавлении задач или новом запуске генератора. Сохраняй существующую схему и оформление, когда смена не нужна.

HTML — рабочее представление. Jira определяет официальный lifecycle, GitHub — состояние PR, приёмка/прод — готовность результата. Пометка в HTML сама по себе не меняет эти системы.

## Статусы и подтверждения

Для существующего артефакта сохраняй его словарь. Последний рабочий вариант использует «Не взято» → «В работе» → «На GitHub» → «Смержено». Это состояние кода, а не полный lifecycle задачи.

- «На GitHub» — есть конкретный PR; различай draft, review, changes requested и CI в деталях.
- «Смержено» — PR действительно merged; открытый PR с зелёным CI сюда не относится.
- Блокер, доступ, требования, ревью, ручная приёмка и прод-проверка — отдельные пометки с источником.
- «Готово» — критерии выполнены; исследование может завершиться решением без PR. «Смержено, ждёт AR/прод-проверки» — нормальное состояние, не Done.
- Для нескольких PR отражай покрытый объём; один merged PR не завершает оставшуюся часть.

Читай текущие Jira-карточки вместе с комментариями и фактические PR/чеки. Фиксируй дату проверки. Старую подпись статуса показывай как снимок, если проверить сейчас не удалось. Не перезаписывай смысл намерения владельца автоматическим маппингом статусов.

Внешние изменения выполняй только в разрешённом объёме, по конфигам и правилам проекта. Если пользователь просит лишь сверку HTML, читай Jira/GitHub без изменения. Не реализуй двустороннюю синхронизацию как неявную часть редактирования артефакта.

## Исполнение и возобновление

Работа по выбранным задачам — [references/execution-loop.md](references/execution-loop.md); ревью — [references/review-protocol.md](references/review-protocol.md); команды — [references/commands.md](references/commands.md). При параллельных исполнителях — сначала [references/agent-economy.md](references/agent-economy.md): ожидание вне модели, роли и модели, размер пакета, гигиена контекста оркестратора.

При переходе между чатами восстанови состояние из файлов и источников, затем продолжай оставшееся. Не перенумеровывай задачи и не переделывай подтверждённо завершённое. Если файлы, браузерный экспорт и серверные статусы расходятся, разбери конфликт до перезаписи.

Храни артефакты в принятой папке проекта. Если репозиторий запрещает локальные планировочные документы в Git, используй согласованную внешнюю папку артефактов; не заводи внутри репо параллельный tracker. В Logos сохраняй личный контекст и ссылки, когда это запрошено, соблюдая его синхронизацию и приватность.

## Проверка и результат

После изменения артефакта: воспроизводимая сборка, уникальность ID, корректные якоря и ссылки, соответствие строк карточкам и состоянию, сохранение прежних статусов; для нового или существенно изменённого интерфейса — визуальная проверка и проверка изменения статуса, экспорта и повторного открытия. Если браузер недоступен, сообщи предел проверки.

После реализации — проверки, требуемые проектом и изменением. Различай «проверки нет», «проходит», «падает» и «не смог запустить». Не заявляй проверки, независимое ревью, push, merge или deploy, которых не было.

В ответе дай ссылку на HTML, что обновлено, что проверено, актуальные блокеры и ближайший шаг. Для отчёта по задачам укажи PR/результат и оставшуюся приёмку. Отдельно обозначь, менялись ли Jira/GitHub. Не закрывай задачи ради красивой сводки.
